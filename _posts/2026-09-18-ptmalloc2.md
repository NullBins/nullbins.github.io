## 0) 전체 구조

>```c
>char *a = malloc(0x20);
>
>free(a);
>```

- **개발자 입장** : `malloc()` → `메모리 받음`  → `free()` → `메모리 반납`
- **glibc 내부** : `malloc(0x20)` → `glibc malloc` → `[ tcache | fastbin | smallbin | unsorted bin | largebin ] 확인, top chunk 사용` → `Heap`
- free() 동작 : `free(chunk)` → `[ glibc가 재사용 위해 저장해둠 ]` → `bin`

---

## 1) ptmalloc2란?

>```c
>malloc(0x20);
>free(ptr);
>calloc(count, sizeof(size));
>realloc(ptr, sizeof(size));
>```

- 위 처럼 함수를 호출하면 이 함수들이 실제 메모리를 관리해야함.
- 이러한 Linux glibc의 malloc 구현이 ptmalloc2의 allocator이다.

> allocator → 프로그램이 동적 메모리를 요청하고 반환하는 작업을 관리하는 코드
> 

- `malloc(0x20);` 을 호출 할때마다 OS(운영체제)한테 `“저 32바이트 주세요!!!!”` 라고 요청하면 매우 비효율적이다. 왜냐하면 system call을 통해 kernel 모드로 전환 해야하기 때문이다. 이러한 모드 전환은 많은 CPU 싸이클을 소모하는 무거운 작업이다.
- 때문에 OS(운영체제)는 `malloc(0x20);` 으로 힙 메모리 영역을 호출하면, allocator가 OS에 system call(Linux의 `brk` or `mmap` )을 보낸다. → OS는 이 요청한 `0x30` 을 수용할 수 있는 최소 단위인 `4KB(4,096byte → 1Page)`의 Page 단위로 가상 주소를 늘려준다. (***놀랍게도 이 단계에서도 실제 피지컬 RAM과 연결은 되지 않는다*** → 할당 받은 heap 주소에 실제로 Read/Write 를 해야 물리 RAM과 메모리 매핑이 된다)
- 이후 C 라이브러리 glibc allocator가 위의 페이지를 쪼개어 `Chunk` 단위로 관리하여 나눠 준다. → 이때 이 페이지에 있는 chunk를 관리하는 구조가 `arena` 이다. → allocator는 멀티스레드 성능을 위해 여러 `arena` 를 사용할 수 있다.

## 2) Heap이란?

> Heap은 Runtime 중 필요한 메모리를 동적으로 할당하는 메모리 영역이다.
> 

>```c
>#include <stdio.h>
>#include <stdlib.h>
>
>int main(void) {
>	char *p = malloc(100);
>	p[0] = 'A';
>	free(p);
>	
>	return 0;
>}
>```

- 위 코드에서 포인터 **p**가 가리키는 **100바이트** 공간은 heap 메모리 영역에서 관리 된다.

>```text
>Low Address
>┌─────────────────────┐
>│ .text               │ 
>├─────────────────────┤
>│ .data / .bss        │ 
>├─────────────────────┤
>│                     │
>│ Heap                │
>│ ↓ 증가               │
>│                     │
>│                     │
>│ ↑ 증가               │
>│ Stack               │
>├─────────────────────┤
>│ shared libraries    │
>└─────────────────────┘
>High Address
>```

- 위는 단순화 된 메모리 영역 구조인데 실제로는 ASLR, PIE, mmap 등에 따라 훨씬 복잡해진다.
- 용어 정리를 하면
    - **Heap** → 실행중에 관리되는 동적 메모리 영역
    - **Arena** → 위 영역의 chunk를 관리하는 구조
    - **Chunk** → malloc이 관리하는 개별 메모리 단위
    - **Bin** → free된 chunk 목록

## 3) Heap Chunk

> glibc는 Chunk를 관리할 수 있도록 Metadata가 붙은 Chunk를 만든다.
> 

>```c
>char *p = malloc(0x20);
>```

- 위 같이 malloc을 호출 했을때, 정확히 0x20(32바이트) 만큼 떼서 주는게 아니다.
- glibc가 관리할 수 있도록 **Metadata**가 붙은 `chunk` 를 만든다.

>```c
>Chunk
>
>Low Address
>
>+------------------------+
>| prev_size              | 8 bytes
>+------------------------+
>| size + flags           | 8 bytes
>+------------------------+
>|                        |
>| user data              |
>|                        |
>+------------------------+
>
>High Address
>```

- 위 처럼 메타데이터 16바이트(8 + 8 바이트)가 붙는다. (64bit 기준)
- glibc chunk의 내부 구조를 단순화하면 아래와 같이 나타낼 수 있다.

>```c
>struct malloc_chunk {
>	size_t mchunk_prev_size;
>	size_t mchunk_size;
>	
>	struct malloc_chunk *fd;
>	struct malloc_chunk *bk;
>	
>	struct malloc_chunk *fd_nextsize;
>	struct malloc_chunk *bk_nextsize;
>}
>```

- `fd(forward pointer)` → Linked list 상에서 **다음에** 위치한 메모리 블럭을 가리킨다.
- `bk(backward pointer)` → Linked list 상에서 **이전에** 위치한 메모리 블럭을 가리킨다.

> ![IMAGE](/assets/images/Pwnable/image01.png)

- 위의 fd, bk 포인터는 chunk가 `free()` 되면 그 공간을 glibc가 재활용하여 관리하기위해 저장되어 사용된다.

## 4) Allocated Chunk와 Free Chunk의 차이

### 사용중인 Chunk

>```c
>After malloc()
>
>chunk
>↓
>+0x00  +----------------------+
>       | prev_size            |
>+0x08  +----------------------+
>       | size                 |
>+0x10  +----------------------+ ← malloc() return address
>       | AAAAAAAAAAAAAAAA     |
>       | user data            |
>       | AAAAAAAAAAAAAAAA     |
>       +----------------------+
>```

>```c
>char *p = malloc(0x20);
>```

- 위와 같이 malloc을 호출한다면 malloc의 반환 주소는 chunk의 시작 주소가 아닌

>```c
>                     p
>                     ↓
>+-------------------+----------------
>| metadata          | user data
>+-------------------+----------------
>```

- 위 처럼 user data의 시작 주소가 반환된다.
- 즉, chunk address와 malloc return address는 `0x10 바이트` 차이가 날 수 밖에 없다.

## 5) Free chunk 이후 내부 구조

>```c
>free(p); // 메모리 해제 하는 순간
>```

- 위의 사용자 데이터는 더 이상 사용자 소유가 아니다.
- glibc는 그 공간을 자료 구조로 사용할 수 있다.

### Doubly-linked bin 구조

>```c
>+----------------------+
>| prev_size            | size_t(8 bytes)
>+----------------------+
>| size                 | size_t(8 bytes)
>+----------------------+
>| fd                   | 8 bytes
>+----------------------+
>| bk                   | 8 bytes
>+----------------------+
>| 남는 공간(사용 X, 변동 O) |
>+----------------------+
>```

### Singly-linked bin 구조 (tcache, fastbin)

>```c
>+----------------------+
>| prev_size            | size_t(8 bytes)
>+----------------------+
>| size                 | size_t(8 bytes)
>+----------------------+
>| next                 | 8 bytes
>+----------------------+
>| user data            | 8 bytes
>+----------------------+
>```

- 위의 성질 때문에 개발자가 주의하지 않으면 `UAF`, `Double Free`, `Heap Overflow` 와 같은 취약점이 발생할 수 있다.
    - → 왜냐하면 사용자가 이미 `free()`된 chunk를 다시 수정하게 되면 `glibc의 내부 관리 데이터`까지 건드릴 가능성이 생기기 때문이다.

## 6) Alignment
- 64bit glibc에서는 일반적으로 chunk가 16바이트(0x10) 단위로 정렬된다.
- `0x20`, `0x30`, `0x40`, `...`
- 위 처럼 chunk size가 정렬된다. 실제로 glibc 소스에서도 기본 정렬 크기를
> ![IMAGE](/assets/images/Pwnable/image02.png)
>```c
>2 * sizeof(size_t); // default
>```
이와 같이 설명하고 있다.

- 예를 들어서
```c
malloc(0x8);
malloc(0x10);
malloc(0x18);
```
위과 같이 할당한다고 한들 chunk는 필요한 `메타데이터(Metadata)`와 `Alignment`를 고려하여 더 큰 크기로 관리된다.
- 대표적으로 x86-64 구조에선
>```
>malloc(0x1); -> chunk size ≈ 0x20
>malloc(0x18); -> chunk size ≈ 0x20
>malloc(0x19); -> chunk size ≈ 0x30
>```
이와 같이 된다. 보면 최소 chunk size가 `0x20(32바이트)`가 되는것을 볼 수 있는데, 그 이유는 청크가 `Allocated` 일때는 사용자 데이터만 담으면 되지만, `free()`되어 해제된 상태(Free chunk)가 되면 메모리 재사용을 위해 연결 리스트 형태의 포인터로 관리되기 때문에 내부 청크에 `prev_size`, `size`, `fd`, `bk` 포인터들이 채워지게 된다.
- 즉 chunk가 free 되었을때 이 포인터들을 저장하려면 최소 `32바이트`의 공간이 무조건 필요하기 때문이다.
- 근데 보면 `0x18` 사이즈에서는 메타데이터 16바이트를 추가하면 chunk size가 `0x28`이 되어야할 것 같은데, 0x20로 잡히는것을 볼 수 있다.
    - 이는 `prev_size`필드의 **공간 재사용(Overlapping) 특성** 때문이다. (x86-64 기준)
    - `prev_size` 필드는 이전 청크(메모리 상 직전 청크)의 크기 정보를 담는 곳이기 때문에 이전 chunk가 Allocated 상태면, `현재 chunk의 prev_size` 공간은 비어있으므로 이전 청크가 이 놀고있는 8바이트를 땡겨 쓸 수 있기때문에, 현재 chunk는 `size`필드만 추가할 수 있는 8바이트만 추가 하면된다.
- 반면 `0x19`는 최소 `0x19 + 0x8`를 해도 `0x21(33바이트)`이기 때문에 Alignment에 따라 `0x30`의 chunk size가 결정된다.

## 7) size value (with GDB)
- GDB에서 heap을 보면 이와 같은 모습을 볼 수 있다.
```c
char* a = malloc(0x20);
char* b = malloc(0x30);
char* c = malloc(0x80);
char* d = malloc(0x410);
```
> ![IMAGE](/assets/images/Pwnable/image03.png)
- 위 처럼 chunk size가 `malloc size + metadata(0x10)` 외에도 `+1` 되는 이유는 바로 `size` 필드의 `size + flag` 때문이다.
```text
mchunk_size = [실제 size] + [상태 flag]
```
- **Flag value & mean (glibc)**
    - `P(PREV_INUSE)`: `0x1` (이전 chunk가 사용중)
    - `M(IS_MAPPED)`: `0x2` (mmap으로 할당)
    - `A(NON_MAIN_ARENA)`: `0x4` (main 아레나가 아닌 arena 소속)
- 때문에 `size = 0x31` 이면 실제론 `chunk size = 0x30` + `PREV_INUSE = 0x1` 이다.

---

## 8) PREV_INUSE Flag
- `PREV_INSUE` 플래그는 위에서 설명했다시피 이전 chunk가 사용하고 있다는것을 알려주는 플래그 값이다.
- 예를들어 `A chunk`가 `Allocated` 상태면 `B chunk`의 플래그 bit `0x1`는 A가 쓰고있다는 의미로 해석된다.
- 만약 `A = free`, `B = Allocated` 되면 B의 P bit는 `0x0`가 될 수 있다.
> ![IMAGE](/assets/images/Pwnable/image04.png)

## 9) Boundary Tag
- `PREV_SIZE`가 있다는걸 알 수 있는데, 그럼 왜 이걸 쓰는가에 대한 의문을 풀어줄 수 있는것이 바로 `Boundary Tag`이다.
- `A chunk`와 `B chunk`를 예시로 들어 이해를 해보자면
```json
{
    "A chunk",
    "prev_size",
    "size": "0x100",
    "data"
}
{
    "B chunk",
    "prev_size": "0x100",
    "size",
    "data"
}
```
- 위 처럼 `B.prev_size`는 바로 앞인 `A chunk`의 size인것을 알 수 있다.
- 이와 같은 구조의 장점이 무엇이냐하면 `B chunk 주소`만 알고 있어도,
`A주소 = B 주소 - B.prev_size`로 계산하면 이전 chunk A를 역산할 수 있는 장점이있다.
```text
---
B addr = 0x1000
B.prev_size = 0x100
---
A addr = 0x1000 - 0x100 = 0x0f00
---
```
- 위 처럼 계산할 수 있는것이다.
- 이렇게 앞뒤 크기 정보를 이용하는 방식이 바로 `Boundary Tag` 라고 볼 수 있다.
> ![IMAGE](/assets/images/Pwnable/image05.png)
- 때문에 `A chunk의 footer`는 `B chunk의 prev_size`인 셈이라고 칠 수 있다.

---

## 10) Boundary Tag의 필요 이유
- 그렇다면 이러한 Boundary Tag가 필요한 이유를 생각해 볼 수 있는데, 그 이유는 바로 `chunk의 병합`을 위해 존재한다고 볼 수 있다.
```c
+---------+
| A free  | 0x100 Byte
+---------+
| B free  | 0x100 Byte
+---------+
```
- 위와 같은 상황일때, 0x100 사이즈인 free chunk를 2개를 그대로 관리할 수 있다.
- 하지만 이 2개의 chunk를 합쳤을때, `0x200짜리 free chunk`로 사용할 수도 있다.
    - 이러한 작업을 바로 **Consolidation / Coalescing**이라고 한다.
    - glibc같은 경우에 `prev_size`와 `size`를 확인하고 `P bit`를 이용해 주변 chunk가 free인지 확인하고 필요하다면 **chunk 병합**을 시도 하게된다.

## 11) Arena란?
- 다음으로 Arena는 Chunk 위의 관리 계층이다. 이러한 Arena는 다음과 비슷한 정보를 가지고 있다.
```text
Arena
│
├── fastbins
│
├── unsorted bin
│
├── smallbins
│
├── largebins
│
├── top chunk
│
└── 여러 관리 정보
```
```c
struct malloc_state
```
- 실제로 glibc에 위와 구조가 존재하며 arena의 상태를 관리한다.
```c
#define chunk_main_arena(p) (((p)->mchunk_size & NON_MAIN_ARENA) == 0)
```
- 대표적으로 위와같은 `main_arena`이다.

---

## 12) 다수의 Arena가 필요한 이유

- 이는 멀티스레드 프로그램을 생각해보면 쉽다.
```text
Thread 1
Thread 2
Thread 3
```
- 이 Thread들이 아래와같이
```c
malloc();
free();
```
- 호출한다고 가정한다 했을때, Arena가 하나뿐이면 Allocator 내부 자료구조를 수정할 때 동기화 문제가 생긴다.
```text
Thread1 ─┐
Thread2 ─┼── main arena
Thread3 ─┘
```
- lock 경쟁이 많아질 수 있다. 때문에 glibc는 여러 arena를 사용할 수 있다.
```text
Thread1 → Arena A
Thread2 → Arena B
Thread3 → Arena C
```
>```text
>하지만 정확히, 1 Thread = 1 Arena 인것은 아니다.
>```

- arena 생성에는 제한이 있고, 필요하면 여러 thread가 arena를 공유한다.

## 13) main arena & non-main arena

> ![IMAGE](/assets/images/Pwnable/image06.png)

- 첫 번째로 주요 Arena인 `main arena`가 있다.
```c
#define chunk_main_arena(p) (((p)->mchunk_size & NON_MAIN_ARENA) == 0)
```
- Chunk의 `size`에는
```c
#define NON_MAIN_ARENA 0x4
```
- 위와 같은 A bit가 있다.
```text
A = 0 → main arena
A = 1 → non-main arena
```
- 위처럼 이해하면 된다.
```text
size = 0x35
---
0x30 = chunk size
0x04 = NON_MAIN_ARENA
0x01 = PREV_INUSE
```
- 위 값들을 토대로 계산해보면
>```text
>0x30 | 0x4 | 0x1 = 0x35
>```
이처럼 될 수 있다.
