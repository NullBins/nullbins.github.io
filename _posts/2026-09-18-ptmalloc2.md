## 0) 전체 구조

>```c
>char *p = malloc(0x20);
>
>free(p);
>```

- **개발자 입장** : `malloc()` → `필요한 메모리 받음` → `사용` → `free()` → `메모리 반납`
- **glibc 내부** : `malloc()` → `ptmalloc2 allocator` → `Arena에서 사용할 Chunk 탐색` → `없으면 Top Chunk / OS에게 추가 메모리 요청`
- **free() 내부** : `free(chunk)` → 바로 OS에게 돌려주는 것이 아니라 대부분 재사용을 위해 allocator 내부 자료구조에 저장

>```mermaid
>flowchart LR
>    P["Program"] --> M["malloc / free"]
>    M --> A["ptmalloc2 Allocator"]
>    A --> AR["Arena"]
>    AR --> C["Heap Chunk"]
>    AR --> B["Bins"]
>    AR --> T["Top Chunk"]
>    T --> OS["brk / mmap → Kernel"]
>```

> **유의 사항** : *glibc allocator는 버전에 따라 세부 구현과 크기 기준이 달라질 수 있다.*

## 1) ptmalloc2

>```c
>malloc(0x20);
>free(ptr);
>calloc(count, sizeof(size));
>realloc(ptr, sizeof(size));
>```

- 위 함수들은 프로그램에서 매우 간단하게 호출할 수 있지만 실제로는 내부에서 메모리를 찾고 나누고 합치고 다시 재사용해야한다.
- Linux의 `glibc malloc` 구현은 ptmalloc 계열 allocator를 기반으로 동작한다.

> allocator → 프로그램이 요청한 동적 메모리를 할당하고, 반환된 메모리를 다시 관리하는 코드

- 만약 `malloc(0x20)`을 호출할 때마다 Kernel에게 매번 새로운 메모리를 요청한다면 `매우 비효율적`이다.
- Kernel 영역으로 넘어가는 `system call`은 일반 함수 호출보다 비용이 크기 때문에 glibc는 어느 정도의 메모리 영역을 확보한 뒤 내부에서 `Chunk` 단위로 잘라서 관리한다.

>```mermaid
>flowchart TB
>    M["malloc(0x20)"] --> G["glibc malloc"]
>    G --> R{"재사용 가능한 Chunk가 있는가?"}
>    R -->|"있음"| C["기존 Free Chunk 재사용"]
>    R -->|"없음"| T["Top Chunk 사용"]
>    T --> S{"Top Chunk도 부족한가?"}
>    S -->|"아니오"| C2["Top Chunk 분할"]
>    S -->|"예"| K["brk / mmap 등을 통해 메모리 확보"]
>```

- 핵심은 `malloc()`을 할때마다 곧바로 `OS에 메모리 요청`하지 않는다는 것이다.

## 2) Heap이란?

> **Heap**은 Runtime 중 필요한 메모리를 `동적`으로 할당하는 메모리 영역이다.

>```c
>#include <stdio.h>
>#include <stdlib.h>
>
>int main(void) {
>	char *p = malloc(100);
>
>	if (p == NULL) return 1;
>	free(p);
>	
>	return 0;
>}
>```

- 위 코드에서 `p`라는 포인터 변수 자체는 `Stack`에 존재할 수 있다.
- 하지만 `p`가 가리키는 `malloc(100)`으로 얻은 메모리는 `Heap` 영역에서 관리된다.

>```text
>Low Address
>┌──────────────────────────┐
>│ .text                    │
>├──────────────────────────┤
>│ .data / .bss             │
>├──────────────────────────┤
>│                          │
>│ Heap                     │
>│ ↓                        │
>│                          │
>│ mmap 영역 / libraries     │
>│                          │
>│ ↑                        │
>│ Stack                    │
>└──────────────────────────┘
>High Address
>```

- 위 구조는 이해를 돕기위한 그림이다.
- 실제 주소 배치는 `ASLR`, `PIE`, `mmap`, Thread 등의 영향으로 훨씬 복잡하다.

- 용어를 먼저 구분하면
    - **Heap** → 동적 메모리가 위치하는 메모리 영역
    - **Arena** → 여러 Chunk와 Bin, Top Chunk 등을 관리하는 allocator의 관리 단위
    - **Chunk** → malloc이 관리하는 개별 메모리 블록
    - **Bin** → 반환된 Free Chunk를 크기와 목적에 따라 보관하는 자료구조

## 3) Heap Chunk

> **glibc**는 사용자가 요청한 데이터 공간 앞뒤에 allocator가 관리하기 위한 정보를 배치하여 `Chunk` 단위로 관리한다.

>```c
>char *p = malloc(0x20);
>```

- 사용자는 `0x20` 바이트를 요청했지만 glibc는 단순히 `32바이트`만 잘라서 주는 것이 아니다.
- Chunk에는 `prev_size`, `size`와 같은 **메타데이터(Metadata)**가 존재한다.

>```mermaid
>flowchart TB
>    subgraph Chunk["할당된 Chunk (x86-64 기준)"]
>        direction TB
>        P["+0x00 · prev_size → 8 bytes"]
>        S["+0x08 · size + flags → 8 bytes"]
>        U["+0x10 · malloc()이 반환하는 User Data"]
>        P ~~~ S
>        S ~~~ U
>    end
>    classDef metadata fill:#fef3c7,stroke:#92400e,color:#111827
>    classDef userdata fill:#dbeafe,stroke:#1e40af,color:#111827
>    class P,S metadata
>    class U userdata
>```

- x86-64 기준 `size_t`가 8바이트이기 때문에 header를 단순하게 보면 `16바이트`처럼 보인다.
- 하지만 실제 malloc request를 Chunk size로 변환할 때는 `prev_size`의 공간 재사용 특성 때문에, 단순히 항상 `요청 크기 + 0x10`으로 계산하면 안된다. (이 부분은 뒤 `Alignment`에서 자세히)

## 4) malloc_chunk 구조체

- glibc의 Chunk 구조를 이해할 때 아래 형태를 알고 있으면 매우 편하다. ([bootlin 참고](https://elixir.bootlin.com/glibc/glibc-2.44/source))

> ![IMAGE](/assets/images/Pwnable/image01.png)

- 여기서 모든 필드가 항상 동시에 의미있는 값을 가지는 것이 아니다.
- Chunk가 `Allocated` 상태인지 `Free` 상태인지, 어느 `Bin`에 들어가 있는지에 따라 같은 메모리 공간의 의미가 달라진다.

- 주요 필드를 정리하면
    - `mchunk_prev_size` → 이전 Chunk가 Free 상태일 때 이전 Chunk의 크기를 저장
    - `mchunk_size` → 현재 Chunk의 크기 + 상태 Flag
    - `fd` → Free Chunk 연결 리스트에서 다음 Chunk
    - `bk` → Free Chunk 연결 리스트에서 이전 Chunk
    - `fd_nextsize`, `bk_nextsize` → Largebin에서 크기 순서 관리를 위해 추가적으로 사용

>```text
> ( Allocated 상태 )
>[ prev_size ][ size ][              사용자 데이터              ]
>
> ( Free 상태의 일반적인 Doubly-linked Bin )
>[ prev_size ][ size ][ fd ][ bk ][ ... ]
>```

- 즉 `free()`가 호출된 뒤에는 원래 사용자가 쓰던 데이터 영역 일부가 allocator의 `연결 리스트 포인터` 저장 공간으로 재사용될 수 있다.

## 5) Chunk 주소와 malloc 반환 주소

>```c
>char *p = malloc(0x20);
>```

- 여기서 `p`는 Chunk 시작 주소를 받는 것이 아니다.
- 일반적인 x86-64 Chunk에서는 Metadata 뒤의 `User Data` 시작 주소를 받는다.

>```mermaid
>flowchart TB
>    C["chunk → 청크 시작 주소"]
>    R["p → malloc이 반환한 포인터"]
>    subgraph Chunk["할당된 Chunk"]
>        direction TB
>        P["+0x00 · prev_size"]
>        S["+0x08 · size + flags"]
>        U["+0x10 · 사용자 데이터 : AAAAAAAA…"]
>        P ~~~ S
>        S ~~~ U
>    end
>    C --> P
>    R -->|"chunk + 0x10"| U
>    classDef metadata fill:#fef3c7,stroke:#92400e,color:#111827
>    classDef userdata fill:#dbeafe,stroke:#1e40af,color:#111827
>    class P,S metadata
>    class U userdata
>```

>```text
>chunk = 0x555555559290
>p = 0x5555555592a0
>
>차이 = 0x10 바이트
>```

- 따라서 Heap 문제를 분석할 때 `pwndbg` 등의 도구가 보여주는 `Chunk Address`와 프로그램이 출력한 `malloc pointer`가 `0x10` 차이 나는 장면을 자주 볼 수 있다.

## 6) Allocated Chunk와 Free Chunk의 차이

### Allocated Chunk

>```mermaid
>flowchart TB
>    subgraph A["Allocated Chunk"]
>        direction TB
>        P["prev_size"]
>        S["size + flags"]
>        U["사용자 데이터 : AAAAAAAA…"]
>        P ~~~ S
>        S ~~~ U
>    end
>    classDef metadata fill:#fef3c7,stroke:#92400e,color:#111827
>    classDef userdata fill:#dbeafe,stroke:#1e40af,color:#111827
>    class P,S metadata
>    class U userdata
>```

- Allocated 상태에서 사용자 데이터를 프로그램이 자유롭게 사용할 수 있다.

### Free Chunk

>```c
>free(p); // 메모리 해제 하는 순간
>```

- `free()`가 호출되는 순간 해당 메모리는 더 이상 프로그램의 소유가 아니다.
- glibc는 그 공간을 재사용하기 위해 allocator 내부 자료구조로 사용한다.

>```mermaid
>flowchart TB
>    subgraph F["Free Chunk (Doubly-linked Bin)"]
>        direction TB
>        P["prev_size"]
>        S["size + flags"]
>        FD["fd → 다음 Free Chunk"]
>        BK["bk → 이전 Free Chunk"]
>        R["나머지 공간"]
>        P ~~~ S
>        S ~~~ FD
>        FD ~~~ BK
>        BK ~~~ R
>    end
>    classDef metadata fill:#fef3c7,stroke:#92400e,color:#111827
>    classDef links fill:#fce7f3,stroke:#9d174d,color:#111827
>    class P,S metadata
>    class FD,BK links
>```

- 이 차이가 Heap 취약점에서 **매우 중요**하다.
- 이미 `free()`한 Chunk를 계속 사용하면 `UAF(Use-After-Free)`가 되고 잘못된 쓰기가 allocator의 연결 정보까지 덮을 수 있다.

## 7) Size 필드와 Flag

- `mchunk_size`는 단순한 크기만 저장하지 않는다.
- 정렬 때문에 하위 비트 일부가 남기 때문에 해당 비트를 상태 Flag로 사용한다.

> ![IMAGE](https://dreamhack-lecture.s3.amazonaws.com/media/4b0c74248164c0b89c3c47d2beed97fd3b22a268520eb070b8c613e70b0d2fb9.png)
> *[사진 출처 : Dreamhack 참고](https://dreamhack.io)*

- **주요 Flag**
    - `P (PREV_INUSE)` = `0x1` → 바로 이전 Chunk가 사용중이라는 의미
    - `M (IS_MMAPPED)` = `0x2` → 해당 Chunk가 mmap 계열로 직접 할당되었다는 의미
    - `A (ALLOCATED_ARENA / NON_MAIN_ARENA)` = `0x4` → main arena가 아닌 Arena에 속한다는 의미

>```text
>size field = 0x31
>
>0x30 = 실제 Chunk Size
>  +
>0x01 = PREV_INUSE
>```

- 따라서 gdb에서 `0x31`, `0x41`, `0x91` 같은 값을 볼 수 있다.
- 실제 크기를 볼 때는 Flag bit를 분리해서 생각해야 한다.

## 8) PREV_INUSE

- `PREV_INUSE`는 현재 Chunk 기준으로 **바로 앞 Chunk의 상태**를 표현한다.

>```mermaid
>flowchart LR
>    A["Chunk A · Allocated"] --> B["Chunk B · size의 P bit = 1"]
>```

- 위 상황에서 `B.size & 1 == 1` 이라면 B의 바로 앞 Chunk A가 사용중이라는 뜻이다.

> ![IMAGE](/assets/images/Pwnable/image04.png)
- 실제로 `OR` 연산을 통해 P bit를 세팅하고, `AND` 연산을 통해 `PREV_INUSE`인지 확인한다.

- 반대로 이전 Chunk가 실제로 병합 가능한 Free Chunk가 되면 다음 Chunk의 `PREV_INUSE`가 `0`으로 관리될 수 있다.

> **중요** : tcache와 fastbin에 들어간 `작은 Chunk`는 즉시 주변 Chunk와 병합되지 않는 경로가 존재한다. 따라서 단순히 `free(A)` 했다고 언제나 바로 `B chunk의 P bit = 0`이 되는 것은 아니다.

## 9) Size value (with GDB)
- 실제로 GDB에서 heap을 보면 이와 같은 모습을 볼 수 있다.
```c
char* a = malloc(0x20);
char* b = malloc(0x30);
char* c = malloc(0x80);
char* d = malloc(0x410);
```
> ![IMAGE](/assets/images/Pwnable/image03.png)
- 위 처럼 chunk size가 `malloc size + metadata(0x10)` 외에도 `+1` 되는 이유는 바로 `size` 필드의 `size + flag` 때문이다.
```text
mchunk_size = [실제 size] |= [상태 flag]
```
- 때문에 `size = 0x31` 이면 실제론 `chunk size = 0x30` + `PREV_INUSE = 0x1` 이다.

## 10) Boundary Tag란?

- Heap Chunk는 인접한 Chunk를 빠르게 찾아서 병합할 수 있어야 한다.
- 다음 Chunk의 `prev_size`를 이용하면 현재 주소에서 이전 Chunk의 시작 주소를 역산할 수 있다.

>```mermaid
>flowchart TB
>    subgraph A["Chunk A"]
>        AS["size = 0x100"]
>        AD["data"]
>    end
>    subgraph B["Chunk B"]
>        BP["prev_size = 0x100"]
>        BS["size + flags"]
>        BD["data"]
>    end
>    A ~~~ B
>```

>```text
>Chunk B Address = 0x1000
>B.prev_size = 0x0100
>
>Chunk A Address = 0x1000 - 0x0100 = 0x0f00
>```

> ![IMAGE](/assets/images/Pwnable/image05.png)
- 실제로 **glibc**에서 [ `chunk address` ] - [ `prev_size` ] 를 하는것을 볼 수 있다.

- 즉 B의 위치만 알고 있어도 `B.prev_size`를 이용해 바로 앞 Chunk A의 시작 위치를 계산할 수 있다.
- 이러한 앞/뒤 경계 정보를 이용해 인접 Chunk를 찾는 구조를 `Boundary Tag`라고 한다.

## 11) Boundary Tag와 Chunk 병합

- Free Chunk가 계속 따로 존재하면 Heap이 작은 조각으로 나뉘는 현상이 심해질 수 있다.
- 따라서 가능한 경우 인접한 Free Chunk를 하나의 큰 Chunk로 합친다.

>```mermaid
>flowchart LR
>    A["Free Chunk A (0x100)"] --> B["Free Chunk B (0x100)"]
>    B --> C["병합"]
>    C --> D["Free Chunk (0x200 범위)"]
>```

- 이러한 작업을 `병합`(`Consolidation` 또는 `Coalescing`)이라고 한다.
- ptmalloc2는 주변 Chunk의 크기와 `PREV_INUSE` 등의 정보를 이용해 병합 가능 여부를 판단한다.

>```mermaid
>flowchart TB
>    subgraph Adjacent["인접한 청크 → 병합 (0x200)"]
>        direction TB
>        A["청크 A → free → 청크 크기 0x100"]
>        B["청크 B → free → 청크 크기 0x100"]
>        A ~~~ B
>    end
>    classDef freed fill:#dcfce7,stroke:#166534,color:#111827
>    class A,B freed
>```

> *단, tcache / fastbin처럼 성능을 위해 병합을 지연하는 경로도 존재한다.*

## 12) Alignment

- x86-64 glibc에서는 일반적으로 Chunk 크기가 `0x10(16)` 바이트 단위로 정렬된다.
    - `0x20`, `0x30`, `0x40`, `0x50`, `...`

- 따라서 사용자가 애매한 크기를 요청해도 내부 Chunk 크기는 정렬된 값으로 올라간다.

> ![IMAGE](/assets/images/Pwnable/image02.png)
>```c
>2 * sizeof(size_t); // default
>```
- 실제로 **glibc 소스**에서도 기본 정렬 크기를 이 처럼 설명하고 있다.

>```text
>x86-64 Chunk size 결과
>
>malloc(0x1)  → chunk size 0x20
>malloc(0x18) → chunk size 0x20
>malloc(0x19) → chunk size 0x30
>```
- 위를 확인하면 최소 chunk size가 `0x20(32바이트)`가 되는것을 볼 수 있는데, 그 이유는 청크가 `Allocated` 일때는 사용자 데이터만 담으면 되지만, `free()`되어 해제된 상태(Free chunk)가 되면 메모리 재사용을 위해 연결 리스트 형태의 포인터로 관리된다.
    - 때문에 내부 청크에 `prev_size`, `size`, `fd`, `bk` 포인터들이 채워지게 된다.

>```mermaid
>flowchart LR
>    R1["request = 0x18"] --> A1["Alignment"] --> C1["Chunk = 0x20"]
>    R2["request = 0x19"] --> A2["Alignment"] --> C2["Chunk = 0x30"]
>```
- 여기서 `0x18 + 0x10 = 0x28`인데 왜 `0x30`이 아니라 `0x20`인걸 보면 헷갈릴 수 있다.
- 이유는 다음 Chunk의 `prev_size` 영역을 앞 Chunk가 Allocated 상태일 때 사용자 공간의 일부처럼 활용할 수 있는 구조 때문이다.
    - `prev_size` 필드는 이전 청크(메모리 상 직전 청크)의 크기 정보를 담는 곳이기 때문에 이전 chunk가 Allocated 상태면, `현재 chunk의 prev_size` 공간은 비어있으므로 이전 청크가 이 놀고있는 8바이트를 땡겨 쓸 수 있기때문에, 현재 chunk는 `size`필드만 추가할 수 있는 8바이트만 추가 하면된다.
- 반면 `0x19`는 최소 `0x19 + 0x8`를 해도 `0x21(33바이트)`이기 때문에 Alignment에 따라 `0x30`의 chunk size가 결정된다.

## 13) Arena란?

- Arena는 Heap Chunk를 관리하는 상위 관리 구조라고 보면 된다.
- 내부적으로 `malloc_state`라는 구조를 통해 여러 `Bin`, `Top Chunk`, `Lock 정보` 등을 관리한다.

>```mermaid
>flowchart LR
>    A["Arena → malloc_state"]
>    A --> F["fastbins"]
>    A --> U["unsorted bin"]
>    A --> S["smallbins"]
>    A --> L["largebins"]
>    A --> T["top chunk pointer"]
>    A --> LB["last_remainder"]
>    A --> LK["lock / 연결 정보"]
>```

- 여기서 tcache는 Arena 내부 Bin과 성격이 조금 다르다.
- tcache는 Thread별 캐시로 사용되며 Arena lock 경쟁을 줄이고 작은 할당을 매우 빠르게 처리하기 위해 존재한다.

## 14) Main Arena와 Non-Main Arena

- 프로그램이 시작되면 대표적으로 `main_arena`가 존재한다.
- 멀티스레드 환경에서는 필요에 따라 추가 Arena가 만들어질 수 있다.

>```mermaid
>flowchart LR
>    T1["Thread 1"] --> MA["main arena"]
>    T2["Thread 2"] --> A2["non-main arena"]
>    T3["Thread 3"] --> A3["non-main arena"]
>```

- 하지만 정확히 `1 Thread = 1 Arena`는 아니다.
- Arena 개수에는 제한이 있으며 여러 Thread가 같은 Arena를 공유할 수도 있다.

- Chunk의 `size` Flag 중 `A(NON_MAIN_ARENA)` bit를 통해 해당 Chunk가 main arena가 아닌 Arena 소속임을 표현할 수 있다.

>```text
>A = 0 → main arena (0b000 : 0x0)
>A = 1 → non-main arena (0b100 : 0x4)
>```

> ![IMAGE](/assets/images/Pwnable/image06.png)
- `NON_MAIN_ARENA`값이 상수값 `0x4`로 지정되어 있다. main 아레나 검사는 `AND` 연산, non-main 아레나 세팅은 `OR` 연산으로 더하는 것을 볼 수 있다.

> [ `size field 계산` ]
>```text
>size field = 0x35
>
>0x30 = Chunk Size
>0x04 = NON_MAIN_ARENA
>0x01 = PREV_INUSE
>
>0x30 | 0x04 | 0x01 = 0x35
>```

## 15) 다수의 Arena가 필요한 이유

- 여러 Thread가 동시에 `malloc()` / `free()`를 호출한다고 가정한다.
- Arena가 하나뿐이면 모든 Thread가 같은 allocator 자료구조를 수정하려고 하기 때문에 lock 경쟁이 커질 수 있다.

>```mermaid
>flowchart LR
>    T1["Thread 1"] --> A["Arena 1개"]
>    T2["Thread 2"] --> A
>    T3["Thread 3"] --> A
>```

- 여러 Arena를 사용하면 상황에 따라 Thread들이 서로 다른 Arena를 사용하여 lock 경쟁을 줄일 수 있다.

>```mermaid
>flowchart LR
>    T1["Thread 1"] --> A1["Arena A"]
>    T2["Thread 2"] --> A2["Arena B"]
>    T3["Thread 3"] --> A3["Arena C"]
>```

- 즉 Arena는 단순한 Chunk 목록이 아니라 동시성을 고려한 allocator 관리 단위이다.

## 16) Top Chunk

- Arena에서 아직 일반 Chunk로 나누어 쓰지 않은 큰 남은 공간을 `Top Chunk`라고 한다.
- 적당한 Free Chunk를 찾지 못했을 때 Top Chunk를 잘라서 새로운 Chunk를 만들 수 있다.

>```mermaid
>flowchart TB
>    H["Heap 영역"] --> A["Allocated Chunk A"]
>    H --> B["Allocated Chunk B"]
>    H --> F["Free Chunk"]
>    H --> T["Top Chunk · 아직 남아있는 큰 공간"]
>```

> **malloc 요청** → **재사용 가능한 Chunk 없음** → **Top Chunk 크기 충분** → **Top Chunk 일부를 잘라 새 Chunk 반환**

- Top Chunk까지 부족하면 allocator는 `brk`, `mmap` 등의 방법으로 추가 메모리를 확보할 수 있다.
