## 0) 전체 구조

>```c
>char *p = malloc(0x20);
>
>free(p);
>```

- 위 코드에서 glibc에서는 대부분의 경우 이 Chunk를 바로 OS에게 돌려주는 것이 아니라 **다음 malloc에서 재사용**하기 위해 보관한다.
- 이때 Free Chunk를 크기와 목적에 따라 관리하는 자료구조가 `Bin`이다.
- 여기서 **Bin**은 binary의 bin을 의미하지 않고 `recycle bin`처럼 재활용 쓰레기통과 같은 보관함을 뜻한다.

>```mermaid
>flowchart LR
>    F["free(p)"] --> T{"tcache에 들어갈 수 있는가?"}
>    T -->|"Yes"| TC["tcache"]
>    T -->|"No"| FB{"fastbin 대상인가?"}
>    FB -->|"Yes"| FAST["fastbin"]
>    FB -->|"No"| C["인접 Chunk 병합 검사"]
>    C --> U["unsorted bin"]
>    U --> S["smallbin"]
>    U --> L["largebin"]
>```

- 아래와 같이 free된 chunk가 `bin`에 들어간다.

>```mermaid
>flowchart LR
>    A["작은 Chunk의 빠른 재사용"] --> B["tcache / fastbin"]
>    C["일반적인 Free Chunk의 대기 장소"] --> D["unsorted bin"]
>    E["크기별로 정리된 Free Chunk"] --> F["smallbin / largebin"]
>```

## 1) Bin이 필요한 이유

- 프로그램은 같은 크기의 메모리를 여러 번 할당하고 해제하는 경우가 매우 많다.

>```c
>char *a = malloc(0x20);
>free(a);
>
>char *b = malloc(0x20);
>```

- 만약 `free(a)`를 했을 때 메모리를 곧바로 OS에게 반환하고, `malloc(0x20)`을 할 때 다시 OS에게 요청한다면 매우 비효율적이다.
- 그래서 allocator는 반환된 Chunk를 내부에 보관했다가 조건이 맞으면 다시 돌려준다.

>```mermaid
>flowchart LR
>    A["malloc(0x20)"] --> C1["Chunk A"]
>    C1 --> F["free(A)"]
>    F --> B["Bin에 저장"]
>    B --> M["다음 malloc(0x20)"]
>    M --> R["기존 Chunk A 재사용"]
>```

- 즉 Bin의 가장 중요한 목적은 **Free Chunk**의 **빠른 재사용**이다.

---

## 2) Chunk Size 구분

- Bin은 `malloc request size`가 아니라 내부적으로 계산된 `Chunk size`를 기준으로 생각해야 한다.

>```c
>malloc(0x20);
>```

- x86-64 glibc에서 위 request는 대표적으로 `0x30` 크기의 Chunk가 된다.

>```mermaid
>flowchart LR
>    A["malloc request = 0x20"] --> B["metadata / alignment 적용"]
>    B --> C["chunk size = 0x30"]
>```

- 따라서 gdb에서 `tcachebins`를 봤을 때 `0x30` 항목에 Chunk가 들어가있다.

>```mermaid
>flowchart LR
>    R["malloc(0x20)"] --> C["Chunk Size 0x30"]
>    C --> B["free() 후 0x30 Size Class에서 관리"]
>```

## 3) 전체 Bin 구조

- ptmalloc2에서 자주 보게 되는 Bin들을 큰 그림으로 정리하면 다음과 같다.

>```mermaid
>flowchart TB
>    F["Free Chunk"] --> TC["tcache (Thread Cache)"]
>    F --> FB["fastbin (작은 Chunk)"]
>    F --> UB["unsorted bin (임시 대기)"]
>    UB --> SB["smallbin (작은 크기별 정리)"]
>    UB --> LB["largebin (큰 Chunk 크기 순 정리)"]
>```

- 성격을 정리하면
    - `tcache` → Thread별 초고속 캐시
    - `fastbin` → 작은 Chunk를 빠르게 재사용하기 위한 Arena 내부 단일 연결 리스트
    - `unsorted bin` → 병합된 Free Chunk가 일단 들어가는 임시 대기 장소
    - `smallbin` → 작은 Free Chunk를 정확한 Chunk size별로 분류
    - `largebin` → 큰 Free Chunk를 크기 순서까지 고려하여 관리

## 4) tcache란?

> tcache = Thread Cache

- tcache는 작은 메모리 할당/해제를 매우 빠르게 처리하기 위해 사용하는 Thread별 cache이다.
- 같은 Thread에서 자주 사용하는 작은 Chunk를 Arena의 복잡한 자료구조까지 가지 않고 빠르게 재사용할 수 있게 해준다.

>```mermaid
>flowchart LR
>    T1["Thread 1"] --> TC1["tcache 1"]
>    T2["Thread 2"] --> TC2["tcache 2"]
>    T3["Thread 3"] --> TC3["tcache 3"]
>```

- 즉 tcache는 `main_arena`의 일반 Bin과 완전히 같은 개념은 아니다.
- 각 Thread가 자신의 cache를 가지고 있다는 점이다.

---

## 5) tcache의 자료구조

- tcache는 Size Class별로 Chunk를 보관한다.
- glibc 2.3x 계열에서는 각 Size Class에 기본적으로 제한된 개수의 Chunk를 저장한다.

>```text
>[tcache]
>
>0x20 : chunk → chunk → ...
>0x30 : chunk → chunk → ...
>0x40 : chunk → chunk → ...
>0x50 : chunk → chunk → ...
>...
>```

- 같은 Size Class 안에서는 단일 연결 리스트 형태로 관리된다.

>```mermaid
>flowchart LR
>    H["tcache[0x30]"] --> C["Chunk C"]
>    C --> B["Chunk B"]
>    B --> A["Chunk A"]
>    A --> N["NULL"]
>```

- 일반적으로 가장 최근에 들어간 Chunk가 가장 먼저 나오는 `LIFO` 성격을 가진다.

>```text
>free(A)
>free(B)
>free(C)
>
>tcache head → C → B → A
>
>다음 malloc() → C 반환
>```

---

## 6) tcache Chunk 내부

- Allocated 상태에서는 사용자가 쓰던 영역이 `free()` 이후 tcache 관리 정보로 사용될 수 있다.

>```mermaid
>flowchart TB
>    subgraph T["tcache에 들어간 Free Chunk"]
>        direction TB
>        P["prev_size"]
>        S["size + flags"]
>        N["next → 다음 tcache entry"]
>        K["key → 중복 free 탐지 등에 사용"]
>        R["나머지 공간"]
>        P ~~~ S
>        S ~~~ N
>        N ~~~ K
>        K ~~~ R
>    end
>    classDef metadata fill:#fef3c7,stroke:#92400e,color:#111827
>    classDef links fill:#fce7f3,stroke:#9d174d,color:#111827
>    class P,S metadata
>    class N,K links
>```

- 현제 glibc에서는 tcache의 `next`가 메모리에 항상 raw pointer 그대로 저장되는 것은 아니다.
- Safe-Linking이 적용된 버전에서는 forward pointer가 주소 기반 값과 XOR되어 저장된다.

> 메모리에 보이는 값 != 항상 실제 next 주소

## 7) tcache가 빠른 이유

- tcache에서 조건이 맞는 Chunk를 찾으면 복잡한 Bin 탐색이나 Arena lock 경로를 상당 부분 줄일 수 있다.

>```mermaid
>flowchart LR
>    M["malloc"] --> T{"tcache에 Chunk 존재?"}
>    T -->|"Yes"| R["즉시 반환"]
>    T -->|"No"| A["Arena 내부 탐색"]
>```

- 그래서 작은 malloc/free를 반복하는 프로그램에서 성능상 이점이 크다.

>```c
>for (int i = 0; i < 10000; i++) {
>    char *p = malloc(0x20);
>    free(p);
>}
>```

- 위와 같은 패턴에서 매번 복잡한 Arena 자료구조를 건드리는 것보다 Thread-local cache를 사용하는 편이 훨씬 효율적이다.

## 8) fastbin이란?

- fastbin도 작은 Free Chunk를 빠르게 재사용하기 위한 자료구조이다.
- 하지만 tcache와 달리 Arena 내부의 `malloc_state`에 속한다.

>```mermaid
>flowchart TB
>    A["Arena / malloc_state"] --> F1["fastbin size class A"]
>    A --> F2["fastbin size class B"]
>    A --> F3["fastbin size class C"]
>```

- fastbin도 같은 크기별로 단일 `연결 리스트` 형태로 관리된다.
- 일반적으로 `LIFO` 방식으로 동작한다.

>```text
>free(A)
>free(B)
>free(C)
>
>fastbin head → C → B → A
>```

---

## 9) fastbin의 중요한 특징 (*즉시 병합하지 않는다*)

- 일반적인 Free Chunk는 주변에 Free Chunk가 있으면 병합할 수 있다.
- 하지만 fastbin은 빠른 처리가 목적이기 때문에 작은 Chunk를 일단 빠르게 넣어두고 즉시 병합하지 않는 경로를 사용한다.

>```mermaid
>flowchart LR
>    A["Chunk A · free"] --> F["fastbin"]
>    B["Chunk B · free"] --> F
>    F --> N["당장 A+B 병합하지 않음"]
>```

- 이후 allocator가 필요하다고 판단하면 `malloc_consolidate()` 같은 경로에서 fastbin Chunk들을 꺼내 주변 Free Chunk와 병합할 수 있다.

>```mermaid
>flowchart LR
>    A["fastbin"] --> B["필요 시 consolidation"]
>    B --> C["인접 Free Chunk와 병합"]
>    C --> D["unsorted bin 등으로 이동"]
>```

- 따라서 Heap 분석에서 `free()`된 Chunk라고 해서 언제나 다음 Chunk의 `PREV_INUSE`가 즉시 해제되는 것은 아니다.

## 10) tcache와 fastbin의 관계

- 최신 glibc에서 작은 Chunk를 free하면 보통 tcache 조건을 먼저 만족하는지 확인하게 된다.
- tcache가 해당 Size Class에서 Chunk를 더 받을 수 있다면 fastbin까지 내려가지 않을 수 있다.

>```mermaid
>flowchart TB
>    F["free(small chunk)"] --> T{"tcache에 공간 있음?"}
>    T -->|"Yes"| TC["tcache"]
>    T -->|"No"| FB["fastbin 가능 여부 검사"]
>    FB --> FAST["fastbin"]
>```

>```text
>[ tcache 기본 count가 7인 환경 ]
>
>1~7번째 free → tcache
>8번째 free 이후 → fastbin 경로 가능
>```

- 정확한 숫자는 환경마다 확인해야 한다.

---

## 11) unsorted bin이란?

- unsorted bin은 이름 그대로 아직 크기별 Bin에 완전히 정리되지 않은 Free Chunk들이 잠시 들어가는 장소이다.
- fastbin / tcache가 아닌 일반적인 Free Chunk가 병합된 뒤 일단 unsorted bin으로 들어가는 흐름을 볼 수 있다.

>```mermaid
>flowchart LR
>    F["free(chunk)"] --> C["앞/뒤 Chunk 병합 검사"]
>    C --> U["unsorted bin"]
>```

- unsorted bin은 `Doubly-linked list` 구조를 사용한다.
- Chunk 내부의 `fd`, `bk`가 실제로 사용된다.

>```mermaid
>flowchart TB
>    subgraph U["Unsorted Bin Chunk"]
>        direction TB
>        P["prev_size"]
>        S["size + flags"]
>        FD["fd"]
>        BK["bk"]
>        D["나머지 데이터"]
>        P ~~~ S
>        S ~~~ FD
>        FD ~~~ BK
>        BK ~~~ D
>    end
>```

---

## 12) unsorted bin을 거치는 이유

- 방금 반환된 Chunk가 곧바로 다음 malloc 요청에 딱 맞을 수도 있다.
- 그렇다면 굳이 먼저 크기별 Bin에 정리했다가 다시 찾는 것보다 unsorted bin에서 빠르게 재사용하는 것이 효율적일 수 있다.

>```mermaid
>flowchart LR
>    F["free(0x250 chunk)"] --> U["unsorted bin"]
>    U --> M{"다음 malloc에서 사용 가능?"}
>    M -->|"Yes"| R["바로 재사용 가능"]
>    M -->|"No"| S["적절한 smallbin / largebin으로 분류"]
>```

- 따라서 `free(small chunk)`를 했다고 무조건 즉시 smallbin에 들어가는 것은 아니다.
- `free(large chunk)`도 마찬가지로 보통 unsorted bin을 거친 뒤 allocator가 unsorted bin을 처리하는 과정에서 largebin으로 정리될 수 있다.

---

## 13) unsorted bin leak이 가능한 이유

- unsorted bin은 Arena의 Bin header와 연결되는 Doubly-linked list이다.
- 그래서 Free Chunk의 `fd`, `bk`에 libc 내부 Arena 관련 주소가 들어가는 상황이 생길 수 있다.

>```text
>Free Chunk
>+0x00 prev_size
>+0x08 size
>+0x10 fd → libc 내부 main_arena 계열 주소
>+0x18 bk → libc 내부 main_arena 계열 주소
>```

- 만약 UAF 등의 취약점으로 free된 Chunk의 내용을 읽을 수 있다면 libc 주소를 Leak할 수 있는 기반이 될 수 있다.

>```mermaid
>flowchart LR
>    U["UAF Read"] --> C["Unsorted Chunk fd / bk"]
>    C --> L["libc 내부 주소 Leak"]
>    L --> B["libc base 계산 가능성"]
>```

## 14) smallbin이란?

- smallbin은 비교적 작은 Free Chunk들을 정확한 **Chunk Size별**로 분류하는 Bin이다.
- 한 smallbin 안에 들어있는 Chunk들은 모두 같은 크기이다.

>```text
>smallbin[0x30]
>    ↕
>0x30 Chunk ↔ 0x30 Chunk ↔ 0x30 Chunk
>
>smallbin[0x50]
>    ↕
>0x50 Chunk ↔ 0x50 Chunk
>```

>```mermaid
>flowchart TB
>    S["Smallbins"] --> B1["0x30 Size Class"]
>    S --> B2["0x40 Size Class"]
>    S --> B3["0x50 Size Class"]
>```

- 같은 Size Class끼리 묶여 있으므로 malloc이 정확한 크기의 Chunk를 빠르게 찾을 수 있다.

---

## 15) smallbin 동작 특성

- smallbin은 같은 크기의 Chunk만 관리하므로 필요한 Size Class를 바로 확인하면 된다.

>```mermaid
>flowchart LR
>    A["malloc이 0x30 Chunk를 필요"] --> B["smallbin[0x30] 확인"]
>    B --> C["Chunk가 있으면 꺼내 사용"]
>```

- smallbin에 들어간 Chunk들은 `fd`, `bk`로 연결된다.

---

## 16) largebin이란?

- largebin은 큰 Free Chunk들을 관리한다.
- smallbin과 가장 큰 차이는 한 Bin에 **서로 다른 크기의 Chunk가 함께 존재할 수 있다는 점**이다.

>```text
>largebin
>
>Chunk A = 0x510
>Chunk B = 0x560
>Chunk C = 0x620
>Chunk D = 0x700
>```

- 따라서 단순 연결 순서뿐만 아니라 크기 순서를 효율적으로 관리할 필요가 있다.

>```mermaid
>flowchart LR
>    A["0x510"] <--> B["0x560"]
>    B <--> C["0x620"]
>    C <--> D["0x700"]
>```

- largebin Chunk에서는 `fd`, `bk` 외에 `fd_nextsize`, `bk_nextsize`가 사용될 수 있다.

---

## 17) largebin의 Chunk 구조

>```mermaid
>flowchart TB
>    subgraph L["Largebin Free Chunk"]
>        direction TB
>        P["prev_size"]
>        S["size + flags"]
>        FD["fd"]
>        BK["bk"]
>        FN["fd_nextsize"]
>        BN["bk_nextsize"]
>        P ~~~ S
>        S ~~~ FD
>        FD ~~~ BK
>        BK ~~~ FN
>        FN ~~~ BN
>    end
>    classDef metadata fill:#fef3c7,stroke:#92400e,color:#111827
>    classDef links fill:#fce7f3,stroke:#9d174d,color:#111827
>    class P,S metadata
>    class FD,BK,FN,BN links
>```

- `fd / bk` → Bin 내부 Chunk 연결
- `fd_nextsize / bk_nextsize` → 서로 다른 크기의 Chunk들을 크기 기준으로 탐색하기 위한 추가 연결

- 이런 복잡한 포인터 구조 때문에 `largebin attack` 계열 기법이 존재한다.

---

## 18) largebin의 성격

- 큰 Chunk에서 아무 Chunk나 사용하면 낭비가 커질 수 있다.

>```text
>요청 크기 = 0x520
>
>후보 A = 0x530
>후보 B = 0x800
>
>둘 다 요청을 만족하지만
>0x530을 사용하는 편이 남는 공간이 적다.
>```

- 따라서 largebin은 큰 Chunk를 크기별로 정리하여 요청을 만족하는 적절한 Chunk를 찾을 수 있도록 설계되어 있다.

>```mermaid
>flowchart LR
>    R["Request 0x520"] --> A["0x530"]
>    R --> B["0x800"]
>    A --> C["더 작은 잔여 공간"]
>```

- 세부 검색 규칙은 glibc 버전에 따라 달라질 수 있지만, 해당 단계에서는 **largebin = 큰 Free Chunk를 크기 순으로 관리하여 적절한 후보를 찾는 구조**로 이해하면 된다.
